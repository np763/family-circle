P1Media streams have no error handling and are never destroyed on client abort

server.js:216 and server.js:220

Problem

fs.createReadStream(...).pipe(res) has no 'error' listener and no cleanup when the client disconnects.

Failure scenario

(1) A file is deleted between fs.stat and the open, for example someone deletes a post while another member's browser is loading its video. The read stream emits an unhandled 'error' and the whole Node process crashes, taking the app down for the family. (2) Every time a browser aborts a video request, which happens on every seek, pipe() leaves the read stream open and its file descriptor leaks. After enough seeking the server runs out of descriptors and starts failing requests.

Suggested fix

Use stream.pipeline(fs.createReadStream(...), res, () => {}) so errors are handled and the file is closed when the client goes away.

P1Removing a human silently deletes everything they posted as a plush or pet

server.js:45, server.js:55, server.js:111 (posted_by_id ... ON DELETE CASCADE), and the delete-member handler

Problem

posts, comments and events cascade-delete on posted_by_id, and so do poll_votes.cast_by_id. The confirmation only says the member's own posts, replies and votes will go.

Failure scenario

An admin removes Dad. Every post, reply, event and poll vote Dad made while acting as "Mr Bear" or "Rex" is deleted too, along with other members' replies on those posts and the uploaded photos and videos. The pets' shared history is wiped with no warning that it includes their content.

Suggested fix

Make posted_by_id and cast_by_id ON DELETE SET NULL (or reassign to the admin), and change the dialog to say exactly what will be deleted.

P1Edit and delete permission ignores the identity being acted as

server.js:617 (same pattern for comments and events)

Problem

The check is post.posted_by_id === s.user.id || post.author_id === s.user.id. s.user is always the real human, so author_id === s.user.id can never match a plush or pet author. The s.user.is_admin part is also dead, because admins are blocked from posts earlier.

Failure scenario

Mum acts as Mr Bear and sees Bear's posts, but only the human who wrote a post can edit or delete it. A child who switches to Bear to fix a typo in a post Dad wrote as Bear gets no Edit button and a 403 from the API, which breaks the "assume the plush's identity" model.

Suggested fix

Compare against s.effective.id as well: allow when post.author_id === s.effective.id or post.posted_by_id === s.user.id, and mirror it in can_edit.

P1Unauthenticated login attempts block the event loop and can dodge the throttle

server.js:398 (and the checkPassword call just above it)

Problem

Every login attempt, including for unknown usernames (a dummy hash is computed on purpose), runs crypto.scryptSync, which blocks the single Node thread for tens of milliseconds. The throttle key is ip|username, so changing the username each time avoids it.

Failure scenario

Anyone who can reach the port (for example when run with HOST=0.0.0.0 on the home network) can spam login requests with random usernames. Each one stalls the server, so uploads, video streaming and every other request for the family stall too. The throttle map also grows without bound.

Suggested fix

Throttle per IP as well as per username, use the async crypto.scrypt, and prune old entries from the attempts map.

P1Stated Node requirement is wrong, so the app fails to start on some supported versions

package.json:1 ("engines": { "node": ">=22.5" }) and the README

Problem

node:sqlite was added in Node 22.5 behind --experimental-sqlite. It only loads without the flag from 22.13 (and 23.4).

Failure scenario

Someone follows the README on Node 22.5 to 22.12. npm start throws "No such built-in module: node:sqlite" and the app never starts, even though their version is within the documented range.

Suggested fix

Set engines and the README to Node 22.13 or newer (or 24 LTS), or add the flag to the start script.
